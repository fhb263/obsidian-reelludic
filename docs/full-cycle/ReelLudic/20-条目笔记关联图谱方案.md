# ②-3 条目笔记关联图谱 · 方案对比

> 用户原话（m00353 ②-3）：「增强统计页（如词云，各模块排序分组要对齐）；现媒体库内笔记全是孤立笔记不关联 ⇒
> 给几个适配生成条目笔记关联图谱的思路，或按类型枢纽笔记」
>
> 用户裁定（2026-11-12）：「先只出方案，不动代码」⇒ **本文只做方案，本轮不实现图谱。**

## 一、先把病因说准（否则方案会打错靶）

### 1.1 现状核查结论

| 核查项 | 事实 | 位置 |
| --- | --- | --- |
| 条目笔记会写双链吗 | **会，但只有三处**：`## 关联`（出边）、`## 链接`（外链）、`## 阅读截图`（图片嵌入） | `src/data/noteGenerator.ts:228 relatedNoteLines()` 产出 `- 关系词：[[目标标题]]` |
| 属性区（导演/作者/演员/丛书/开发商/专辑）写的是链接吗 | **不是，全是纯文本** | 笔记属性表格由 `generateNoteMarkdown()` 拼，字段值原样输出 |
| 已有图谱功能吗 | **有，但是"一圈"不是"网络"**：只画以当前条目为中心的一圈放射图，⛔ 不做全库力导向大图 | `src/pure/relatedGraph.ts`（#635，只存出边、入边渲染时算） |
| 关联数据从哪来 | **只有手动**：`MediaEntry.related: RelatedLink[]`，用户自己一条条挂 | `src/data/types.ts:403` |

### 1.2 病因（RCA）

用户看到的现象是「笔记全是孤立笔记」。往下追三层：

1. **表象**：Obsidian 原生图谱里每个条目笔记都是一个孤点。
2. **直接原因**：笔记文件里几乎没有 `[[…]]` 出链 —— 因为绝大多数条目的 `related` 是空的（手动挂关联的人很少）。
3. **根因**：**条目之间天然存在的共享属性（同一导演、同一作者、同一丛书、同一开发商的其它作品）从来没有被写成链接。**
   这些数据本来就躺在 catalog 里（`director` / `cast[]` / `author` / `artist` / `series` / `developer` / `platform` / `album` / `genres[]` / `tags[]`），
   但它们是**属性值**，不是节点 ⇒ 两本同一个作者的书之间没有任何路径可走。

> 一句话：不是"缺一个图谱视图"，是"**数据里没有可供成边的公共节点**"。
> 现有 `relatedGraph` 只能画用户手动连的边；手动边太少，图就必然是孤点。

### 1.3 一个必须正视的取舍

把「作者名」直接写成 `[[刘慈欣]]` 会**在库根目录生成一堆作者笔记**（Obsidian 对未创建的 wikilink 点一下就建空文件）。
十本书的作者全链接 = 库里多出十个几乎空的笔记文件，而用户要的是"专业、极客、轻量"（③-5 的定位）。

⇒ 方案的核心分歧就在这：**公共节点放哪**。
下面三个方案沿着这条轴展开，成本由低到高。

---

## 二、方案 A：类型枢纽笔记（用户提名的那条，成本最低）

### 2.1 做什么

按**属性种类**生成固定数量的枢纽笔记，而不是按属性值生成：

```
ReelLudic/枢纽/书籍作者.md      ← 内含按作者分组的 [[条目]] 列表
ReelLudic/枢纽/影视导演.md
ReelLudic/枢纽/丛书系列.md
ReelLudic/枢纽/游戏开发商.md
ReelLudic/枢纽/标签.md
```

枢纽笔记内部：

```markdown
## 刘慈欣
- [[三体]]
- [[球状闪电]]

## 特德·姜
- [[你一生的故事]]
```

同时在**每个条目笔记的属性区**加一行 `枢纽：[[书籍作者]]`（或复用现有 `## 关联` 区的尾部）。

### 2.2 图谱效果

变成 **星形 + 中转**：`条目 → 枢纽 → 条目`。
任意两本同作者的书在图上**两跳可达**，而且中间节点只有 5 个（不是几百个作者名）。
Obsidian 原生图谱立刻从"一堆孤点"变成"几个亮星 + 挂在星上的条目"。

### 2.3 成本与风险

| 维度 | 评估 |
| --- | --- |
| 代码量 | 小：一个纯函数（catalog → 5 份 Markdown）+ 一个"写入既有文件前先比对内容"的落盘函数。复用 `noteGenerator` 的转义与 wikilink 口径 |
| 新增文件数 | **固定 5 个**（不随条目数增长） |
| 与现有双写机制的冲突 | 需注意：这 5 份是**插件托管文件**，用户手改会被覆盖 ⇒ 必须在文件头部写明「本文件由 ReelLudic 生成，手改会在下次同步时被覆盖」 |
| 触发时机 | 建议随"保存条目"做**防抖批量重建**（不是每条目改一次就重建 5 份），或提供手动「重建枢纽」按钮 |
| 增量维护 | 删除条目后，枢纽里那一行要跟着消失 ⇒ 重建时整份重写最稳（5 份文件不大） |

### 2.4 为什么推荐这个作为第一步

- 用户自己提名的方向（"或按类型枢纽笔记"）—— 方向已经对齐，不用重新说服。
- 文件数固定，不污染库；即便用户不喜欢，删 5 个文件就完全回滚。
- 纯函数好测：给定 entries → 期望 Markdown，能钉死每一行。

## 三、方案 B：属性值双链（最"原生"，但会造文件）

### 3.1 做什么

在条目笔记的属性区把属性值直接写成 wikilink：

```markdown
导演：[[克里斯托弗·诺兰]]
丛书：[[银河帝国系列]]
```

### 3.2 图谱效果

最符合 Obsidian 用户的直觉：**同名节点自动合并**，`诺兰` 一个节点连着所有他的片。
图形质量是三个方案里最高的（真正的网络，不是星形）。

### 3.3 成本与风险（这是它排第二的原因）

- 🔴 **会生成大量空笔记**：每个导演/作者/演员都会变成一个"红链"。活跃用户的库可能几百个这种点开就空的文件。
- 🔴 **同名不同人无法区分**：两个"张伟"、两个"李子"会被合并成一个节点 —— 这是**错误信息**，比没有链接更糟。
- 🔴 **改名即断链**：用户把 `导演：诺兰` 改成 `导演：Christopher Nolan` 后，旧链接指向的节点就孤立了。
- 需要在设置里加开关（默认关），并提供"清理已生成的空节点笔记"的反向操作，否则用户装了以后很难收拾。

### 3.4 可以改造成"无文件"版本

Obsidian 支持 `[显示名](obsidian://...)` 之外的形式吗 —— 不支持。**双链必然对应一个目标名**。
除非……用**块引用**或**标签**（`#诺兰`）。标签不生成文件，但标签会污染用户自己的标签体系（与 ②-3 词云抢同一份 `tags`），不推荐。

---

## 四、方案 C：枢纽笔记 + 图谱视图（成本最高，效果最好）

= 方案 A + 在插件内做一张**跨条目关系图**（复用 `relatedGraph` 的几何代码，但数据源扩成"共享属性"）。

### 4.1 为什么成本高

- 现有 `relatedGraph` 明确写死「只画以当前条目为中心的一圈，⛔ 不做全库力导向大图」——
  那张设计图（`docs/superpowers/plans/2026-10-15-related-graph-design.md`）是用户当年认可的形态，
  扩成全库图等于推翻它，需要重新确认交互（缩放、拖拽、节点数上限、性能）。
- 全库图在 500+ 条目时节点数会到 1000+，SVG 直接渲染会卡；要上 canvas 或分页。

### 4.2 建议

**先做 A，观察用户是否还需要 C。** A 出来以后，Obsidian 原生图谱已经能给出"星形网络"的观感；
如果用户仍觉得"看不清全局关系"，再做 C 才有明确的目标形态。

---

## 五、三方案对比

| 维度 | A 类型枢纽笔记 | B 属性值双链 | C 枢纽 + 图谱视图 |
| --- | --- | --- | --- |
| 新增文件数 | 固定 5 | 每个属性值 1 个（几十~几百） | 同 A |
| 图谱观感 | 星形 + 中转（两跳可达） | 真正的网络（最好） | 网络 + 插件内可视化 |
| 同名不同人 | 无影响（按字段分组，不合并人名） | 🔴 会错误合并 | 同 A |
| 改名断链风险 | 无 | 🔴 有 | 无 |
| 实现成本 | 小 | 中 | 大（需推翻既有"一圈"形态） |
| 回滚成本 | 删 5 个文件 | 要清理红链，麻烦 | 同 A |
| 用户是否已提名 | ✅「或按类型枢纽笔记」 | ❌ | ❌ |

**推荐路径：A 先做（下一轮），B 作为设置项可选（默认关），C 视 A 的效果再定。**

## 六、如果要动手，实现 A 的关键约束（给下一轮的自己）

1. ⛔ **不要碰 `relatedGraph.ts`** —— 那是手动关联的一圈图，与枢纽笔记是两套机制，混在一起会让"出边/入边"口径崩掉。
2. 枢纽笔记必须写**显式的"由插件生成"头**，否则用户手改后被静默覆盖会炸。
3. 重建要**整份重写 + 先比对内容**（内容没变就不写盘），沿用 `src/data/catalog.ts:382 backupBeforeWrite` 的同款"引用相等就跳过"口径。
4. 只在**用户主动开启**时才创建这些文件（默认关）。理由：装插件就凭空往库里塞 5 个文件，对"轻量"是伤害。
5. 归属判断要防脏数据：`director` 是单值、`cast` 是数组、`series` 是单值、`genres` 是数组 —— 逐个字段确认形态再写聚合，⛔ 别用 `Object.values` 一刀切。
6. 单测钉死：给定 3 个条目（两本同作者 + 一本不同）⇒ 作者枢纽里第一个作者下恰好 2 条。
