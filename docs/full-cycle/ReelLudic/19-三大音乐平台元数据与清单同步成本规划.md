## 1. 需求拆解

用户原话：「给三大音乐平台加**搜索元数据**和**同步清单**的功能（参考金标准开源项目，先规划成本）」。

拆成两条独立能力，二者共用采集层但落库语义完全不同：

### 能力 A · 搜索元数据
用户在搜索框搜歌 → 结果卡片除了歌名/歌手，还能带回**专辑、封面、时长、年份**，选中后回填条目。

现有链路**已经能搜到**这些字段（平台响应里有），只是**在映射到卡片时被丢掉了**。

### 能力 B · 同步清单
用户在网易云/QQ/酷狗里「收藏的歌」「我创建的歌单」→ 一键拉回，落成本地条目（或写成歌单条目），与「Steam 同步游戏库 / 微信读书同步书架」同构。

现有链路的 `dlRecommendedPlaylists` / `dlPlaylistSongs` 走的是**公开推荐歌单**，不是用户私有资源 —— 这是本需求真正的工作量所在。

## 3. 参考项目怎么用（不是照搬）

用户点名的五个项目分两类，用途不同：

### 3.1 统一搜索接口层 —— `music-lib` / `go-music-api` / `Meting-Agent`

这类项目的价值**不在代码**，在于它们维护了「各平台接口 → 统一响应结构」的**映射表**，且持续跟进平台改版。

- 本仓**已经有**统一层（`DlSearchResult` / `DownloadSong`），所以不需要引入它们的运行时。
- 真正值得抄的是它们的**字段映射完整度**：网易云 `al.picUrl`、QQ `albummid → cover`（`https://y.gtimg.cn/music/photo_new/T002R300x300M000{albummid}.jpg`）、酷狗 `albumpic` —— 本仓 `pure/dl/qq.ts` 目前填的 `coverUrl` 是否走这条，需实现时逐个核对。
- **建议**：实现时把三家的「封面 URL 拼接规则」收敛成纯函数（参照本仓 `pure/steamCover.ts` 的做法），并加一条「全仓不得出现第二处硬编码图床域名」的守卫。成本约 0.5 人日，收益是以后改版只改一处。

### 3.2 云端元数据写本地 —— `Music Scraper` / `musify`

它们的做法是「读平台元数据 → 写入本地音频文件的 ID3 标签」。

- 本仓音乐条目已有 `localAudio` 字段（`src/data/types.ts:239`），所以这条路技术上通。
- 但**写 ID3 需要引入新依赖**（`node-id3` 之类），而本仓是 Obsidian 插件、打包产物已是 2.3 MB 级；且 Obsidian 插件侧写二进制标签有权限与跨平台编码风险。
- **建议**：**本轮不做写标签**，只做「元数据写进 catalog.json + 笔记」。若用户坚持要写 ID3，单列一个 3～5 人日的独立批次。

### 3.3 单平台专用 API

三家都**没有**面向第三方的官方开放 API（网易云有 `weapi`/`eapi` 网页接口，QQ 有 `musicu.fcg`，酷狗有移动端接口）。所谓「专用 API」实际就是各自的网页接口，本仓已在用。**不存在「换官方 API 就一劳永逸」的选项**，这点要在决策时讲清楚。

## 4. 方案与工作量

### 阶段 A · 搜索元数据补全（低成本，建议立刻做）

**做法**：不碰采集层，只补映射与类型。

1. `MusicSearchResult` 增可选字段 `duration?`（秒）——`year` 已有不用加；`trackNo` 若确实需要再讨论。
2. `songLibraryResults` 把 `s.coverUrl` → `cover`、`s.duration` → `duration` 传下去。
3. 封面 URL 拼接规则收敛成纯函数（见 3.1）。
4. 结果卡片与属性面板按字段渲染（`EntryForm.svelte` 的音乐分支）。
5. 新增 `tests/songLibrary.test.ts` 断言「四平台封面不丢」，并对新纯函数补用例。

**工作量**：**1.5～2 人日**
**风险**：低。若 `MusicSearchResult` 加字段触发断言守卫（本仓有逐字锁字段表的历史），需同步改判据，已在工时内。

### 阶段 B · 平台内曲目直接落库（中）

**做法**：搜索结果 → 直接建成 `music` 条目，带 `source`/`sourceUrl`/`cover`/`album`/`localAudio`。

1. 新建 `src/pure/musicSync.ts`，照 `steamSync.ts` 四件套写 `MusicSyncCandidate` / `musicEntrySeed` / `musicDetailFields` / `mergeSyncCandidates`。
2. 去重键：`music:{source}:{id}`（与 `steamItemKey` 同构）。
3. schema 决策：曲目号/时长无处放 —— 建议**本轮不加字段**，`album` 存专辑名，时长不落库（列表页已有 `durationMin`，但那是「收听时长」，语义不同，⛔ 不要混用）。
4. `main.ts` 增 `importMusicRows(...)`，落库后 `refreshViews()`。

**工作量**：**3～4 人日**
**风险**：中。`durationMin` 与「歌曲时长」语义撞车是本仓已知的命名陷阱，落库前必须确认用户期望。

### 阶段 C · 同步清单（高，主体工作）

**做法**：带 Cookie 拉「我喜欢 + 我创建的歌单 + 收藏的歌单」，列表弹窗勾选后落库。

拆成 C1 采集 / C2 落库 / C3 入口三块：

#### C1 采集层（最贵）
每家要新增两类接口，且都是私有资源：

| 平台 | 我喜欢 | 我的歌单 | 难度 |
|---|---|---|---|
| 网易云 | `weapi/v3/song/detail` 已有曲目详情，但「我喜欢」需要 `weapi/v1/play/record` 或 `weapi/song/like/get`（接口名随版本变） | `weapi/user/playlist?uid={uin}`，uid 可从 `weapi/nuser/account/get` 取（本仓 `:90 NETEASE_ACCOUNT_API` 已在用） | **中**（加密已有，主要是不确定当前接口名） |
| QQ 音乐 | `musicu.fcg` 的 `music.fcgi` / `favor` 模块 | `musicu.fcg` 的 `music.musicasset.PlaylistBaseRead`（dissid 列表），`extractQqUin` 已有 | **中高**（musicu 的 `req_N` 批量结构较绕，本仓已为 dissCounts 写过一次批量补数） |
| 酷狗 | 需要 `userid` + `token`（Cookie 里取），接口为 `kugou.com/yy/index.php?r=play/getdata` 家族之外的私有路径 | `kugou.com/plist/list/{userid}?json=true` 家族 | **高**（酷狗私有接口文档最差，且要求 `mid`/`dfid` 参数，历史上变化频繁） |

- 每家都要写「Cookie 是否仍有效」的前置校验（可复用 `dlTestConnection`，`ok` 才允许进同步）。
- 每家都要写「拿到空列表」与「接口 302 到登录页」两种失败的可读文案（本仓对失败文案有硬要求：必须能指导用户下一步）。

**工作量**：网易云 2～3、QQ 3～4、酷狗 4～6 人日 ⇒ **小计 9～13 人日**

#### C2 落库层
- `pure/musicSync.ts` 扩展：`MusicSyncSource = 'liked' | 'playlist'`
- 歌单本体：是否要建「歌单条目」？本仓 `MediaEntry` 无「歌单」类型。三条路：
  - (a) 只落单曲，歌单名写进 `album` 或标签 —— 最省，1 人日
  - (b) 歌单落成一条 `music` 条目 + 曲目挂 `series`（本仓有系列机制）—— 中，2～3 人日
  - (c) 新增实体 —— ⛔ 不建议，牵动 schema、统计、视图、笔记生成全链
- 建议 (a)，若用户要「歌单也是一个条目」再升 (b)。

**工作量**：**1～3 人日**（取决于选 a 还是 b）

#### C3 入口与 UI
- `src/modals/MusicSyncModal.ts`（照 `SteamSyncModal` 结构，约 12 KB）
- `main.ts` 增 `openMusicSync(source)` + `fetchMusicSyncCandidates` + `importMusicRows`
- 设置页三条 Cookie 行加「立即同步」按钮（`src/Settings.ts:1101 DL_COOKIE_ROWS` 区，与豆瓣/Bangumi/TMDB/微信读书 的 `rl-sync-btn` 同构）
- 自动同步开关与间隔（参照 `STEAM_AUTO_SYNC_GAP_MS` / `shouldAutoSync`）

**工作量**：**3～4 人日**

**阶段 C 小计：13～20 人日**

## 5. 风险登记

| 风险 | 可能性 | 影响 | 缓解 |
|---|---|---|---|
| 三平台私有接口改版 | **高**（历史上都改过） | 对应平台同步失效，需重做采集层 | 每家采集层独立成 `pure/dl/{platform}.ts` 的纯函数，解析与请求分离；写单测用固定响应样本（本仓 `tests/dl-*.test.ts` 已有此范式） |
| Cookie 过期后用户不理解 | 高 | 报「同步失败」但用户不知去重贴 | 同步前置调 `dlTestConnection`，失败直接给「去设置 › 搜索配置 › 音乐平台重贴 Cookie」的可点指引（`renderHintNote` 支持链接） |
| 网易云 eapi 加密参数变更 | 中 | `neteaseCrypto.ts` 全废 | 已有该文件，改动集中；⚠️ 该文件是全仓唯一加密实现，⛔ 别为实现新需求另写第二份 |
| 版权/VIP 曲目拉得到元数据但下不了 | **必然** | 用户以为「同步了就能下」 | 同步只负责**元数据与条目**，不承诺可下载；列表里对 `vip: true` 明确标注（`DownloadSong.vip` 字段已有） |
| 巨量清单（如「我喜欢」上万首）阻塞主线程 | 中 | 同步卡死 | 照 `STEAM_SYNC_LIMIT = 2000` 设上限 + 分批 + 进度回调（`DownloadProgressCallback` 范式已有） |
| schema 膨胀 | 中 | 牵动 normalize / 笔记生成 / 统计 / 视图全链 | 本轮**不扩 schema**（见 B 阶段第 3 点） |

## 6. 建议排期

1. **第一批（本轮之后立刻可做）**：阶段 A。1～2 人日，用户搜歌立刻能看到封面和时长，投入产出比最高，且**不引入任何风控依赖**。
2. **第二批**：阶段 B。让「搜到的歌」能一键变成条目，闭环「搜索 → 落库」。
3. **第三批（需用户决策后再启动）**：阶段 C。启动前需用户确认三件事：
   - 歌单要不要落成条目（选 a / b）
   - 是否接受「Cookie 过期需手动重贴」
   - 是否接受「私有接口无官方保证，平台改版即失效」

## 7. 待确认决策点（实现前必须由用户裁定）

1. **歌单落库粒度**：只落单曲（a）/ 歌单成条目 + 曲目挂系列（b）。
2. **是否扩 `MediaEntry` schema**：加音乐专属块（曲目号/时长/碟号），还是本轮不加。
3. **是否写本地音频 ID3 标签**（3～5 人日额外成本，需引入依赖）。
4. **「我喜欢」是否算清单**：三家语义不同（网易云「红心」、QQ「我喜欢」、酷狗「我喜欢」），是否需要先把三家统一成一个 `liked` 概念。
5. **是否把三平台注册为正式数据源**（进 `sourceRegistry.PROVIDERS` + 「元数据搜索源启用」表）—— 若注册，则「搜索元数据」会走既有搜索链而不是「在线曲库」卡片，两者语义不同，需明确用户期望哪一条。
