## 1. 需求（用户原话拆解）

> 「海报墙希望能规划一套**系列分类方案**，例如书籍**基地系列**有几部、影视动画**《海绵宝宝》有 17 部**、
> 电影**《熊出没》十几部**、游戏也有若干**衍生作品**；这类**同一 IP 下多部作品**既想**全部收集**又**难以归类**的场景。」

拆成三条硬要求：

1. **全部收集** —— 每一部都必须是**独立条目**（各自有状态 / 我的评分 / 进度 / 笔记），⛔ 不能被合并成一条。
2. **难以归类** —— 海报墙上一屏十几张**同质海报**（熊出没每部海报都是那两只熊），视觉上淹没有效信息，也不知道「还有没有下一部」。
3. **要有序/有组** —— 用户想知道「基地系列我有几部」「熊出没按年排下来长什么样」。

### 1.1 🔴 先分清四类例子，它们**结构不同**

| 例子 | 结构 | 顺序语义 | 现有数据能否支撑 |
|---|---|---|---|
| 基地系列（几部书） | 同一作者 / 世界观的多部**独立长篇** | **阅读顺序**（第 1~7 部；含前传） | ✅ **豆瓣已有「丛书」回填** ⇒ 复用现成 `series` 字段即可命中 |
| 电影《熊出没》十几部 | 同一 IP 的**逐年院线片** | **上映年份** | ❌ 豆瓣无丛书、TMDB 多无 `belongs_to_collection`（国产片尤甚）⇒ **只能手填** |
| **《海绵宝宝》（2026-09-30 已核实，见 §1.2）** | **一个 IP 三层**：① 正剧 **17+ 季**（342+ 集，**已续订至第 19 季**）；② **6 部电影**（**4 部院线 + 2 部 Netflix 流媒体**）；③ **2 部衍生剧**（珊瑚营 / 派大星秀） | 正剧按**季序**；电影按**上映年份** | ❌ 三层都无数据源字段；且**正剧连「一条条目装 17 季」都做不到**（见 §1.2）⇒ 必须靠系列分组 |
| 游戏衍生作品 | 同一 IP 的**主作 + 外传 / 资料片 / 重制** | 常无严格顺序，只要「同一个 IP」 | ❌ 无数据源字段 ⇒ **只能手填** |

⇒ **结论**：方案的核心不是一个「顺序数字」，而是一个 **分组名（必填）+ 组内序号（可选）+ 组内角色（可选）** 的三元组。
序号语义**由用户自定**（阅读序 / 上映序 / 季序都行）—— 这正是 Calibre 的立场（见 §2）。

### 1.2 🔴 为什么「17 季」不是「偏好问题」而是「schema 硬约束」（2026-09-30 代码核实）

用户追问「海绵宝宝不是出到 17 季多了吗」——**对，而这恰恰是 D-45 被问窄的地方**：本仓**根本没有「季」这一维**，
所以一部 17 季的剧**不可能**用一条条目表达。三条代码证据：

| 证据 | 位置 | 后果 |
|---|---|---|
| `progress` 的 `season` 是**单个标量**（`{ season, episode, totalEpisodes, history[] }`），且表单里那个季输入框的 `max` 被钳在 `entry?.progress?.season ?? 1`（**只能前进、不能回退**） | `data/types.ts:61`；`EntryForm.svelte:2003` | `season` 只是「当前看到哪一季」的**指针**，⛔ 不是「这部剧有几季」的容器 |
| 集数组是**扁平索引**：`episodeFiles` / `episodeUrls` / `episodeTitles` 都是 `index 0 = 第 1 集`，长度由 `totalEpisodes` 决定 | `data/types.ts:147-151`；`EntryForm.svelte:491-499 / 1059-1067` | 17 季塞进一条 ⇒ `totalEpisodes = 342` ⇒ 集按钮网格 **342 个格子**，实际不可用 |
| 🔴 **集号解析器把季号丢掉了**：`episodeScan` 的 `S01E05` 规则是 `/(?:^|[\s._[(-])(?:S\d{1,2})?[Ee](\d{1,3})(?!\d)/` —— `S\d{1,2}` 是**可选的非捕获组** | `pure/episodeScan.ts:18` | `S05E03` 与 `S01E03` **都解析成 3** ⇒ 扁平网格下**后一季会覆盖前一季**（「从文件夹批量检索剧集」直接把第 5 季第 3 集填进第 3 格） |

⇒ **实际结论**：在现有 schema 下，用户**只能按季建条目**（17 条），⛔ 不存在「1 条 vs 17 条」的选择余地。
**这不是缺陷、也不该在本批修** —— 给条目加「季」维度（`entry.seasons[]`）会连带波及集按钮网格分段、`episodeScan` 保留季号、
阅读/播放进度、笔记 `progress_season`、追更表全链，是**独立的大工程**（见 D-45(a) 的乙案，⛔ 本批不做）。

🔴 **反过来看，这恰恰强化了本方案的必要性**：17 条「海绵宝宝 第 N 季」+ 6 条电影 = 单看剧集侧就有 17 张同质海报 ——
比熊出没的十几张更极端。系列分组对这类 IP 不是「优化」，是**唯一可用的组织手段**。

⇒ 由此定下三条硬口径：
**① 分组作用域 = 同类型（⛔ 不跨类型）** —— 🔴 **用户 2026-09-30 裁定**：「不做跨类型，比如可以电影一个海绵宝宝系列折叠卡，动画一个海绵宝宝系列折叠卡，其他的不管」；
**② 组内序号必须能表达「季序」**（D-39 → 选 (a)，`seriesIndex` 直接填季号）；
**③ `series` 字段本身要放开到全部 6 类型**（D-40 → 选 (a)）—— 注意这与 ① 不矛盾：**字段全类型可用，但分组键含 `type`**，两者缺一不可。

## 2. 金标准检索（按用户「先检索开源金标准」的交付约定）

| 项目 | 机制 | 对本方案的启发 |
|---|---|---|
| **Calibre**（电子书库，事实标准） | 两条独立字段：`series`（**字符串**，分组名）+ `series_index`（**数值**，支持**小数**：`2.5` = 第 2、3 部之间的中篇，`0.5` = 正传之前的前传）。有「按系列浏览」（tag browser）与**批量元数据编辑**（整批刷同名，再逐个调序号）。🔴 明确警告：**系列名不一致会被当成两个系列**（`The Expanse` ≠ `Expanse`） | ① 字段就该是「名 + 序」两条，⛔ 不要把序号拼进名字（`基地 3`）；② 序号**必须允许小数**；③ 名字要**归一化**（trim / 全半角 / 大小写）才分组；④ 批量打标是真痛点（11 部熊出没逐条填会疯） |
| **TMDB** | `belongs_to_collection`（官方策展的电影合集） | 有则用、无则空 —— **不能当作必需**（国产 IP 覆盖极差）。⚠️ 本仓连不上 TMDB 时也不能阻塞手填 |
| **Infuse**（媒体播放器） | 「系列（Collections）」= **TMDB 藏品 + 自定义系列**两路并存；系列**可跨类型**（「电影、整部电视剧，或者只是电视的季」都能入同一系列）；只在使用媒体库时可见，且**可与普通影片混排显示**（可在设置里关掉） | ① **「数据源给的」与「用户自定义」必须并存**，自定义是主力；② ⚠️ 它**支持跨类型**，但🔴 **本仓按用户 2026-09-30 裁定不做跨类型**（分组限同类型）⇒ **此处刻意偏离金标准**，见 §4.1；③ **折叠/混排要可开关**（有人就是想在墙里看见每一张） |
| **Bangumi** | 关联条目（前传 / 续集 / 同一系列…）—— 是**关系图**不是扁平字段 | ⚠️ 图模型表达力最强但**重**（要新实体 + 新页面）。⚠️ 本仓网络**连不上 bgm.tv**（api.bgm.tv 未实测），本批不取 |
| **Plex / Jellyfin** | Collections（人工策展的集合） | 同上：人工集合永远是主路 |

**综合**：取 **Calibre 的字段口径**（名 + 可小数序号）+ **Infuse 的产品口径**（自定义为主、显示可开关），
**偏离** Infuse 的「跨类型」一项（用户裁定：分组限同类型，见 §4.1），
**不取** Bangumi 的图模型（本批过重）。

### 4.2 🔴 折叠卡的组名 = `${系列名} ${类型}系列`（用户 2026-09-30 追加）

用户原话：「**组名称再区分开来，如海绵宝宝 电影系列、海绵宝宝 动画系列**」。

| 项 | 口径 |
|---|---|
| **组名** | `${series} ${ENTRY_TYPE_LABELS[type]}系列` —— 例：`海绵宝宝 电影系列` / `海绵宝宝 动画系列`。类型名**必须取 `data/types.ENTRY_TYPE_LABELS`**（单一真源），⛔ 别在视图层自造词（否则「动画」写成「番剧」这类漂移必然发生） |
| **`.rl-sub` 不再重复类型** | 原来是「电影 · 6 部」，类型进了组名后改成**只剩数量**（`6 部` / `17 季`），避免同一张卡上「电影」出现两遍 |
| **展开态组头同源** | `.rl-series-head-name` 用**同一个组名**（`熊出没 电影系列`），⛔ 别在折叠卡与组头各拼一次 —— 两处必然漂移（本仓「多个入口各写一套」栽过多次） |
| **为什么必须带类型** | 影视页签「类型 = 全部」下同名两张卡并排，只靠类型色条区分太弱（色觉差异、窄卡、深色主题都会削弱）⇒ **组名自带类型才是自解释的** |
| **对应断言** | S5 要有一条：**同名不同 `type` 的两张折叠卡，组名互不相同且都含「系列」**（仿真页 `sr434` 的【③ 自检②】已先行验证过这个口径） |

⚠️ 超长系列名会走 `.rl-ttl` 既有的 `ellipsis`（单行省略）—— 这是既有行为，⛔ 不为折叠卡另改标题样式。

### 4.1 🔴 作用域规则（D-45(b) 用户裁定后的落地口径）

**裁定原文（2026-09-30）**：「**不做跨类型**，比如可以**电影一个海绵宝宝系列折叠卡**，**动画一个海绵宝宝系列折叠卡**，其他的不管。」

⇒ 落成两条规则，⛔ 别在实现里偷偷放宽：

| 规则 | 口径 |
|---|---|
| **分组键 = `type` + 归一化的系列名** | 同名的「电影组」与「动画/剧集组」**永不合并**。影视聚合页签（`lockType = null`、类型 = 全部）下会**并排出现两张卡**（各带自己的 `×N`），这是**预期行为**、不是 bug |
| **① 筛选胶囊的作用域跟随题材那一套** | `pure/genreFilter.resolveGenreScope` 的先例：**只有作用域内能锁定单一类型时**才提供系列筛选（阅读-文学/网文、影视-动画/电视剧/电影、游戏、音乐各自一套）；`类型 = 全部` 的聚合视图 **`null` = 整块不渲染**。理由：否则同名两个系列会在池里出现两行同名、用户无法分辨 |
| **③ 折叠卡无作用域限制** | 只要当前视图的条目集里有 ≥2 条同 `(type, 系列名)` 就折叠；`类型 = 全部` 下按类型各折各的 |

⚠️ **为什么坚持「字段全类型可用 + 分组限同类型」这两条并存**：字段放开（D-40）是为了让电影/动画/游戏/书籍**都能填**系列名；
分组限同类型（D-45(b)）是为了让「电影一组、动画一组」这个用户明确要的形态成立。
**只要实现里把 `type` 拼进分组键，两条自动同时满足** —— 这是 S3 的关键测试点（见 §6）。

### 6.1 海绵宝宝这条用例的实际形态（按 D-45(a)=甲 + D-45(b)=不跨类型 推演）

| 视图 | 条目 | 分组结果 |
|---|---|---|
| 影视页签 · 类型 = **电影** | 6 部电影（`type='movie'`） | **一张卡** `海绵宝宝 ×6` —— `series = 海绵宝宝`、`seriesIndex` = 上映序（1…6 或按年份） |
| 影视页签 · 类型 = **动画**（或 电视剧） | 17 条「第 N 季」+ 可能的衍生剧（同 `type`） | **另一张卡** `海绵宝宝 ×17` —— `series = 海绵宝宝`、`seriesIndex` = **季号**（1…17） |
| 影视页签 · 类型 = **全部** | 上面两者的合集 | **并排两张卡**（电影一张、剧集一张）。✅ 正是用户要的形态，⛔ 不是 bug |

🔴 **一个意外收益：D-42 原本的真实冲突自动消失了。** 我上一版担心「同一 IP 里季序与电影上映序是两套互不相容的编号」——
但既然分组键含 `type`，**电影组和剧集组各自排序**，两套编号**永不碰面**：
电影组按上映序、剧集组按季号，`seriesIndex` 在两个组里可以各填各的，⛔ 不需要「全组只用一个序」那条妥协。
⇒ D-42 收敛为最简单的一条：**组内 `seriesIndex` 升序 →（无值回落）年份 → 标题**。

⚠️ **用户信息怎么填**（写进表单提示语，⛔ 不写「内部机制」）：系列名填 `海绵宝宝` 即可，序号填「这一作在**本类型里**排第几」。
⚠️ 衍生剧（珊瑚营 / 派大星秀）若也要收进来，因为它们同为 `tv`/`anime` ⇒ 填同名就会并进剧集那张卡（`×19`）；
想分开就填别的系列名 —— **由用户定，工具不裁决**（D-45(c)）。
