# 1.0.4 批次D 设计 — 回收站（软删除） / schema 迁移框架 / 数据健康面板

> 日期：2026-09-14 | 状态：**设计待裁定**（未动代码） | 前置阅读：`docs/superpowers/plans/2026-09-14-1.0.4-plan.md` §⑩
> 目标：把「删了就没了」变成「删了还能捞回来」，并给未来的数据结构变更留出正规通道 —— 而不是等到出事故才补。
> ⚠️ 本稿的回收站方案已按用户 2026-09-14 的裁定**从「文件级回收站目录」改为「单文件回收站」**（原话：「catalog 就没有单文件的备份方案了吗，太多文件我管理不过来」）。

---

## 0. 现状（已核实，非推测）

| 事实 | 证据 |
|---|---|
| 删除 = 从 `catalog.json` 的 entries 里**物理移除** + **删除笔记文件** | `EntryService.removeWithNote()`：`remove(id)` → `io.deleteFile(e.notePath)` |
| **封面图片不删、阅读进度文件也不删** → 直接变孤儿 | `removeWithNote` 只处理 `notePath`；封面另有「清理孤儿封面」工具（`listOrphanPosters` + `PosterCleanupModal`），**阅读进度 `阅读进度/*.json` 没有任何清理入口** |
| 删除入口 3 处，确认已统一为**轻量确认弹窗** | 卡片右键菜单 / 批量栏 / 编辑弹窗（1.0.4 批次C 曾改气泡，同日用户裁定改回轻弹窗） |
| catalog 是**单文件全量重写** | `CatalogStore.save()` 写整个 JSON |
| 已有写前自检 + **单文件**滚动备份 | `catalog-backups.json`（内含最近 5 版快照）；写前 `isCatalogTextConsistent` 不过则中止写入 |
| `version` 字段存在，**但没有迁移框架** | 读取只靠 `normalizeEntry` 白名单兜底（能剔非法值，**表达不了字段改名 / 语义变更**） |

**一句话结论**：现在「删除」是不可逆的，而且**备份也救不回来**（备份救的是"写坏了"，不是"删错了"）。

**数据文件纪律（用户取向）**：媒体库目录下应当**少而集中** —— 目标形态只要 3 个文件：`catalog.json` + `catalog-backups.json` + `回收站.json`。任何新增设计都必须先回答「会不会多出文件」。

## 1. D-1 回收站（软删除，单文件）

### 1.1 三方案与裁定

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 写进 catalog | `catalog.json` 新增 `trash: [...]` | 会让 catalog 越滚越大（用户正担心这件事）；每次加载都要解析回收站 |
| **B. 独立单文件 `回收站.json`（✅ 采用）** | 一个 JSON 存「条目快照 + 笔记正文 + 附属文件路径」 | **零新增文件/目录**；与 `catalog-backups.json` 同构；恢复 = 从 JSON 写回文件 |
| C. 文件级回收站目录 | `回收站/<时间戳>_<id>/`，笔记与封面搬进去 | 文件最多（一删一条就多一个目录）→ 用户明确否掉 |

### 1.2 数据形态

```jsonc
// 媒体库目录/回收站.json
{
  "schema": 1,
  "items": [
    {
      "deletedAt": "2026-09-14 22:15:30",   // 本地时间（与备份时间戳同口径）
      "reason": "user",                      // user | bulk | cleanup
      "entry": { /* MediaEntry 完整快照，含原 id */ },
      "note": { "path": "笔记/movie/某某电影.md", "text": "……笔记全文……" },
      "assets": [                            // 只记路径：不搬文件、不存二进制
        { "kind": "poster", "path": "封面/某某电影.jpg" },
        { "kind": "progress", "path": "阅读进度/某某电影-阅读进度-e_1788....json" }
      ]
    }
  ]
}
```

- **笔记正文存进 JSON**（纯文本、体积小）→ 恢复时写回文件，因此**不移动任何文件**。
- **封面（二进制）不存**：只记路径；恢复时文件还在就继续用，不在就明确提示「封面需重新设置」。回收站因此永远是纯文本单文件。
- 删除 1 条 → 数据文件仍是 3 个，**文件数不随删除条数增长**。

### 1.3 三条路径

**① 删除（软删）**
1. 视图层轻量确认弹窗（已有）→ `plugin.deleteEntry(id, true)`
2. 写 `回收站.json`：追加一条（`entry` 快照 + 笔记正文 + 附属路径）
3. 删笔记文件（`io.deleteFile`）
4. 从 `entries` 移除 → `save(catalog)`
5. Notice：「已移入回收站 · 可恢复」

**崩溃兜底（相比文件移动方案的关键改进）**：回收站存的是**副本**而不是原件，所以顺序是「**先落副本 → 再删原件**」。任一步中断，最坏结果只是回收站里多一条无用记录（无害）；**不会出现「原件没了、快照也没落」的不可恢复状态**。

**② 恢复**
1. 取快照 → `entry.id` **原样保留**（id 是笔记 / 封面 / 进度的命名主键，换 id 会让附属资源全部失联）
2. 写回笔记文件到 `note.path`；**路径已被占用 → 拒绝恢复并提示**（不覆盖别人的文件，也不改名悄悄塞进去）
3. 插回 `entries` → `save()`
4. 从 `回收站.json` 移除该条（封面与进度文件本就没动，无需回搬）

**③ 清空 / 保留策略**
- 保留天数（默认 **30 天**）+ 最大条数（默认 **200 条**），先到即轮转（最旧的先真删）
- 轮转时机：onload + 每次新增条目（纯函数 `trashToPrune(items, { days, max }, now)`，可单测；`max ≤ 0` 兜底为 1，防「策略配成 0 把回收站全清」）
- 「清空回收站」= 清空 items（二次确认，用轻弹窗）

### 1.4 风险与坑

- 🔴 **删除入口必须逐点清点**（批次C 已踩过：第三个入口藏在编辑弹窗）。三处入口走**同一条**软删路径；「彻底删除」只出现在回收站界面内。
- 🔴 **笔记副本写入失败 → 中止删除**：宁可这次删不掉（提示失败），也不能「删掉原件却没存住副本」。
- ⚠️ **`回收站.json` 不参与 vault 监听**（同 `.backups/` 先例），否则写它就会自激刷新。
- ⚠️ **封面不存二进制** → 恢复后若封面文件已被「清理孤儿封面」删掉，恢复流程必须给出「封面需重新设置」的结果，而不是静默空白。
- ⚠️ **回收站自身要有上限**（默认 200 条 / 30 天），否则它会成为下一个"越滚越大"的文件；健康面板（D-3）显示其占用。

### 1.5 待裁定

- **R15-a** 删除时笔记是否一并进回收站？（推荐：**是**；否则"恢复"是半残的）
- **R15-b** 封面 / 阅读进度怎么处理？（推荐：**只记路径**——封面不存二进制、进度文件本来就不会被删，保持单文件）
- **R15-c** 保留策略默认值：**30 天 / 最多 200 条**？
- **R15-d** 回收站入口放哪：设置页「数据」区列表（标题 / 删除时间 / 恢复 / 彻底删除 / 清空）？
- **R15-e** 要不要「撤销删除」即时提示？（推荐：**暂不做**，确认弹窗已降低误删率）

## 2. D-2 schema 迁移框架

### 2.1 现状问题

今天只能做**加法**：新字段给默认值 + `normalizeEntry` 白名单兜底。以下三类变更**没有正规通道**，只能靠人工脚本或干脆不做：
1. **字段改名**（如 `pageCount` → `metaChapters`）
2. **语义变更**（如某个值从"总集数"改成"已看集数"）
3. **结构性重组**（如把 12 个平铺字段收进 `meta: {}`）

### 2.2 设计

`src/pure/migrations.ts`（纯函数 + 单测，不碰 IO）：

```ts
export interface Migration {
    from: number;                       // 起始 schema 版本
    to: number;                         // 目标版本（约定 to === from + 1，链式）
    description: string;                // 人话说明（写进迁移日志，便于回滚排查）
    run: (raw: Record<string, unknown>) => Record<string, unknown>;
}

/** 从 raw.version 逐级升到目标版本；缺环 → 抛错（宁可拒绝加载，也不静默丢数据） */
export function migrateCatalog(raw: unknown, targetVersion: number, steps: Migration[]): {
    data: unknown;
    from: number;
    to: number;
    applied: string[];                  // 本次实际跑过的迁移 description
};

/** 未来版本保护：raw.version > 当前插件支持的版本 → 只读模式（拒绝写入，防降级毁数据） */
export function checkForwardCompat(rawVersion: number, supported: number): 'ok' | 'future';
```

`CatalogStore.load()` 新流程：

```
readText → JSON.parse
  → version = raw.version ?? 1
  → checkForwardCompat：若 raw 版本比插件新 → 返回只读标记 + Notice「此库由更新版本的插件写入，已进入只读模式」
  → migrateCatalog(逐级)
  → normalizeEntry 兜底（与迁移不冲突：迁移做"改名/搬家"，normalize 做"剔非法值"）
  → 返回
```

**迁移前必须留回滚点**：若 `applied.length > 0`，把原始文本另存进**已有的单文件备份**（`catalog-backups.json` 里插一条 `at = "pre-migrate v<旧版本>"`）—— 复用单文件备份，**不额外产生文件**。

**写入时机**：迁移只在内存进行；**首次成功保存时**才把新 `version` 落地。

### 2.3 测试清单（TDD）

- 单步迁移：`{from:1,to:2}` 正确改名 / 保留未涉及字段 / 不改入参
- 链式：1→2→3 顺序正确；`applied` 记录完整
- **缺环**：1→3 没有 2 → 抛错（不静默跳过）
- 版本缺失视为 1；版本已是最新 → 不动
- **未来版本**：raw 版本 > 支持版本 → 只读、不迁移
- 幂等：对已是目标版本的数据重复跑 → 无变化
- 与 `normalizeEntry` 的组合：迁移后的数据仍能被 normalize 正常收编

## 3. D-3 数据健康面板

### 3.1 定位

**先量化，再决定要不要动结构。** 用户问的是"条目过多未来怎么办"——回答不该是猜"应该分片"，而应该是给一组数字，让阈值自己说话。

### 3.2 指标清单（全部只读，不自动改任何东西）

| 分组 | 指标 | 用途 |
|---|---|---|
| 规模 | 条目数 / 三个数据文件的字节数 / 平均条目字节 / **最大的 10 个条目**（字段大小分解） | 判断"大"是来自条目多，还是某几条有超长简介/目录 |
| 完整性 | 缺封面 / 缺年份 / 缺评分 / 缺笔记 的条数（按类型分组） | 找到"半成品"条目 |
| 一致性 | id 重复 / 标题重复 / 被 `normalizeEntry` 剔掉的非法值统计 | 发现脏数据与历史遗留 |
| 孤儿资源 | 未被引用的 `封面/` 文件（**复用 `listOrphanPosters`**）/ 无主 `阅读进度/*.json`（**新增**）/ `笔记/` 下没有对应条目的笔记（**新增**） | 清理体积；点出"删条目时该收走什么" |
| 备份与回收站 | 备份文件字节数 / 快照版数与最旧时间；回收站条数 / 占用 / 最旧一条 | 决定是否清空、是否该收紧保留策略 |

输出形态：设置页「数据」→「数据健康」→ 报告卡片（可「复制为 Markdown」）。**清理动作一律逐项勾选 + 二次确认**（沿用 `PosterCleanupModal` 的交互口径）。

### 3.3 分片阈值建议（回答"以后怎么办"）

| 规模 | 建议 |
|---|---|
| < 1k 条（现在） | 什么都不用做。单文件全量重写 + 单文件备份完全够用 |
| 1k – 5k 条 | 仍不分片。加一条**写入节流**（连续改动合并 1 次写盘）；关注健康面板的"平均/最大条目字节" |
| > 5k 条 或 catalog > 5 MB | 再谈分片。首选**按类型分文件**（`catalog.json` 只留索引）；**不要按时间分片**（跨时间排序/统计会变成 N 次读盘） |

结论：**现在不做分片**，先让数字说话。

## 4. 拆分与实施顺序

| 子批次 | 内容 | 风险 | 说明 |
|---|---|---|---|
| **D-1** | 回收站（软删 + 恢复 + 保留策略 + 清空，单文件） | 🔴 高 | 改删除语义；3 个入口 + 笔记副本 + catalog 写入三处协同 |

每个子批次走既有链路：**象形确认（UI 部分）→ TDD（纯函数同位测试）→ 构建 → 部署测试库 → 三段 cmp → 产物断言 → 文档登记 → 镜像同步**。
