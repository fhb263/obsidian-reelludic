# 书源分类错位诊断 — 「文学源」被网文下载调用（2026-09-30）

## 1. 现象（复核实测）

用户报告：设置页「书籍源凭据 › 经典文学源」下的 **11 条凭据，会被网文下载错误调用**。

**实测证据**（读活动库 `C:/Users/kest/Desktop/临时测试库/.obsidian/plugins/obsidian-reelludic/data.json`）：

```
novelSources total = 11
  kind='novel' -> 0 条
  kind='book'  -> 11 条
    香书小说 xbiqugu.la / 梦书中文 mcxs.info / 鸟书网 99xs.info / 笔趣阁22 22biqu.com /
    笔尖中文 xbiquzw.net / 悠久小说网 ujxsw.org / 阅读库 yeudusk.com / 顶点小说 wxsy.net /
    笔趣阁365 biquge365.net / 燃文小说网 ranwen8.cc / 书海阁小说网 shuhaige.net
```

**结论：11 条全是网文站（笔趣阁系 / 小说站），却全部带着 `kind: 'book'` 标记。**

⇒ 于是：网文条目打开「下载网文」窗口时，`novel` 这一类**一条都没有**，触发**「本类为空 ⇒ 回退到全部」**的兜底，
把 11 条**标着文学**的源整批拿出来搜 / 下。

## 2. 是不是「历史遗留的配置映射问题」？

**是历史遗留，但成因不是「映射表错位」，而是两件事叠加：**

### 根因 A（历史遗留 · 数据层）：一次误触发的整批改分类
`pure/sourceRule.mergeSources` 在 #422 **首版**实现里，把「已存在的站点」也按本次导入按钮的类别**重新打标**
（注释原文保留了这段历史：「这条最初写的是『已存在的跟着改成这次的类』」）。

后果就是设置页那条注释记下的实测事故：
> 用户在「经典文学源」里点了一次导入（想刷新那批源），**10 条老源被整批搬走** ⇒ 换到网文条目里"一条书源都看不见"。

这条 **代码 bug 当时就修好了**（现在 `mergeSources` 第 401~408 行的口径是「`kind` 只给新条目打标；已存在站点一律不动；不传 `kind` 时保留旧分类」），
但 **已经写进 `data.json` 的 11 个 `kind: 'book'` 没有被回滚** —— 代码修了，数据没修。

⚠️ 换句话说：`kind` 是**本地状态**（书源文件里压根没这个键），它的唯一来源就是「当时点的哪个导入按钮」，
所以**没有办法从文件内容反推「这条源本该属于哪一类」** —— 修复只能靠显式操作（见 §4）。

### 根因 B（设计 · 放大器）：`本类为空 ⇒ 回退全部`
两处同口径的兜底（写这个是**有意的**，为的是别让面板空着让用户以为「书源全丢了」）：

| 位置 | 代码 |
|---|---|
| 宿主检索 | `main.searchNovel`：`const mine = this.novelSourcesOf(kind); const sources = mine.length ? mine : (this.settings.novelSources ?? []);` |
| 弹窗面板 | `BookDownload.svelte`：`$: shown = mine.length ? mine : sources;`（并有 `fellBack` 小字提示） |

这个兜底在「根因 A 的脏数据」存在时，就把「标记错了」这件事**从『看不见』升级成『错着用』**：
面板至少还写了「你的书源都在另一类 —— 下面先列出它们（共 11 条）」，
但**搜索结果不会带这条提示**（结果行只说来源名），用户看到的就是「下网文时冒出 11 个文学源」。

### 不是这些原因（已排除）
- ⛔ 不是 `sourceKey` / 站点地址映射错位（`sourceKey` 只用于「同站点算更新」，与分类无关）。
- ⛔ 不是凭据字段串了（`novelSources` 与 `musicDlCookies` / 各 API Key 是彼此独立的键；书源本身不是凭据，只是**这一组叫「书籍源凭据」**）。
- ⛔ 不是 `sourceKindOf` 的缺省值错（缺省 `'novel'` 是对的；这 11 条的 `kind` 是**显式**的 `'book'`，走不到缺省分支）。

## 3. 影响面

1. 「下载网文」窗口列出/搜索/下载时使用 11 条文学源（用户看到的「错误调用」）。
2. 「下载文学」窗口反而是**正确**的（`book` 类非空 ⇒ 不回退，用这 11 条）—— 所以现象只在网文侧暴露。
3. 设置页小节徽标：经典文学源显示「11 条」、网络文学源显示「0 条」—— 与用户心智相反。
4. 「体检」按钮（#432 甲）只体检**本类**，所以点「网络文学源」的体检**什么都不会发生**（`list.length === 0` 直接 return），
   用户会以为体检坏了 —— 这是同一根因的第二个症状。

## 4. 修复思路（三案，待用户裁定）

### 甲 · 数据修复 + 加一枚「整批移到另一组」的显式入口（推荐）
- **数据修复（一次性）**：把这 11 条的 `kind` 从 `'book'` 改回 `'novel'`。
  两条落地方式：
  - (a) 我直接改活动库 `data.json`（最快，但属于「我手改用户数据」，需要用户明确点头）；
  - (b) 在设置页加一枚行头按钮「**全部移到「网络文学源」**」（在 `renderSourceSubsection` 的行头 `.rl-src-tools` 里追加一枚），
    用户自己点一次 —— 与既有「移到另一组」（`setNovelSourceKind`）**同一实现**，只是作用于整组。
    好处是**以后任何一次弄错都能一键纠回**，不是一次性的手术。
- 优点：治本（数据回到正确分类）+ 补上「整组改分类」这个缺失能力（现在只能逐条点 11 次）。
- 代价：一个新按钮（UI 改动 ⇒ 按约定要先给象形对比）。

### 乙 · 收紧兜底（去掉「回退全部」）
- 本类为空 ⇒ 显示空态 + 明确 CTA「去设置页把这批源移到本类」。
- ⛔ **不建议单独用**：这正是 #422 续二**刻意加**的兜底，去掉会回到「书源全不见了、要重新导入」那个已被实测抱怨过的形态。
- 若要用，必须**同时**有 §4 甲的「整批移动」入口，才能让空态里的 CTA 一步可达。

### 丙 · 甲 + 乙 组合（推荐给「要彻底」的场景）
- 数据修好 + 整批移动入口 + 空态里的 CTA 指向那个入口（而不是指向逐条点）。
- ⛔ 兜底**保留**，但把 `fellBack` 那行小字从「下面先列出它们」改成「**下面先列出它们（建议去设置页一次移过来）**」。

### 不做的事
- ⛔ 不按站点域名/源名**自动猜**该属于哪一类（「笔趣阁系 = 网文」这种启发式一定会误伤真正的文学站，且违背「不猜」的既有纪律）。
- ⛔ 不动 `sourceKindOf` 的缺省值（它现在是正确的）。
