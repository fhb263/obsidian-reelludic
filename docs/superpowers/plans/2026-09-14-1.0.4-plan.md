### 方案（推荐 A）

**A. 纯函数 + 统一渲染**
- 新增 `src/pure/emptyState.ts`：`resolveEmptyState({ lockType, statusFilter, typeFilter, kindFilter, query, poolCount, filteredCount })` → `{ kind: 'no-data' | 'no-match', title, hint, action }`

  - `poolCount > 0 && filteredCount === 0` → `no-match`（标题「没有匹配的条目」，hint 回显生效筛选，动作 = 「清除筛选」）
- 表格视图补 `<tr><td colspan="8">` 空态行。
- 样式收敛到 styles.css 单一 `.rl-empty` 块（追番表 `.rl-tr-empty` 合并，避免双份漂移）。

**B. 只补表格空态（最小改动）** — 不动现有文案结构。风险最低，但「筛选无结果误导」问题保留。

## 3. ③ 无障碍 Accessibility（Tab 逻辑为主）

### 现状核实（`HomeView.svelte:176-196` 等）

已有：`role="tablist"` / `role="tab"` / `aria-selected` / `.rl-tabs button:focus-visible`；卡片 `role="link" tabindex="0" on:keydown`；批量栏 `aria-label`。

缺口（按优先级）：

| 级别 | 缺陷 | 位置 |
|---|---|---|
| P0 | 一级页签**无 roving tabindex**：6 个页签全在 Tab 序列内，键盘要按 6 次才能越过 | `HomeView.svelte` `.rl-tabs` |
| P0 | 页签**无方向键导航**（←/→/Home/End），不符合 ARIA APG | 同上 |
| P0 | 页签**无 `aria-controls`**；`.rl-tab-body` **无 `role="tabpanel"`** / `id` / `aria-labelledby` / `tabindex="0"` | 同上 |
| P0 | **瀑布流卡片键盘不可达**：`.rl-m-card` 只有 `on:click`，无 `role`/`tabindex`/`keydown` | `MediaList.svelte:681` |
| P0 | **分组歌单行键盘不可达**：`.rl-music-row` 同上 | `MediaList.svelte:546` |
| P1 | **表头排序键盘不可达**：`.rl-th-sort` 是可点 `<th>`，无 `tabindex`/`role="button"`/`aria-sort` | `MediaList.svelte:707-711` |
| P1 | `<table>` 无 `<thead>/<tbody>`，`<th>` 无 `scope="col"` | `MediaList.svelte:704` |
| P1 | 互斥选中态只有视觉 `class:on`，读屏不知选中：类型 chips / 书籍分类 chips / 视图切换 / 追番表-排期表切换 | MediaList / HomeView |
| P1 | `role="link"` 卡片**内含交互子元素**（⋯ / 打开笔记 / 观看 / 状态徽标），读屏语义冲突 | `MediaList.svelte:583` |
| P2 | 右键菜单 `.rl-menu` / `.rl-ctx` 无 `role="menu"`（EntryForm 的已加，MediaList 未加） | `MediaList.svelte` |
| P2 | 空态 `.rl-empty` 无 `role="status"`（结果数变化不播报） | 全视图 |
| P2 | 分页器（本版新增）需 `aria-label` + `aria-current="page"` | 新增 |

### 方案（推荐 A）

**A. 纯函数 + 三处收敛**
- 新增 `src/pure/tabNav.ts`：`resolveTabKey(key, currentIndex, count)` → `{ index, activate }`；支持 `ArrowLeft/ArrowRight/Home/End`，**回绕**（APG 推荐）。TDD 覆盖边界（单 tab / 首尾回绕 / 无关按键返回 null）。
- 一级页签：`tabindex={activeTab === t ? 0 : -1}` + `on:keydown` → 纯函数算目标 → `switchTab()` + `focus()`；`aria-controls` 与 panel `id` 对应；`.rl-tab-body` 加 `role="tabpanel"` + `aria-labelledby` + `tabindex="0"`。
- 互斥按钮组补 `aria-pressed`：类型 chips、书籍分类 chips、视图切换、追番表/排期表。
- 补 P0 两处键盘不可达（瀑布流卡片、分组歌单行）：`role="link" tabindex="0" on:keydown(Enter)` + `:focus-visible` 环（与海报墙卡片同形态）。
- P1 表头排序：`<th>` 内包 `<button class="rl-th-sort">` 并补 `aria-sort`；同时补 `<thead>/<tbody>` + `scope="col"`。

**B. 全量改造（含 `role="link"` 卡片语义重构）** — 收益更大但触及卡片 DOM 与读屏名，风险与回归面大，建议拆到 1.0.5。

**C. 仅补 P0 四项** — 最小改动，先把「键盘完全够不到」的路堵上。

## 4. ④ 设置页「数据源凭证」折叠面板 Collapse 失效（已定位根因）

### 根因（确定，非猜测）

`styles.css:194` 用的是**后代选择器**：

```css
.rl-key-open .rl-key-body { display: flex; }        /* ← 命中所有后代 */
.rl-key-open .rl-key-caret { transform: rotate(90deg); }
```

而 1.0.3 的层级是**三层嵌套**：

```
① 数据源管理         .rl-fold  > .rl-fold-body            （createFoldout，有持久化）
   └ 数据源凭据       .rl-key-row > .rl-key-body          （createSubfold，无持久化）
      ├ 豆瓣          .rl-key-row > .rl-key-body          （createApiKeyRow）
      ├ TMDB          .rl-key-row > .rl-key-body
      └ …
```

- (c) 只让 `.rl-tabs` 吸顶，工具栏/筛选栏不吸（改动最小，收益也最小）。

## 10. ⑩ catalog.json 的发展方向（删除数据保留 + 大库演进）

### 现状事实（已核实代码）

| 维度 | 现状 |
|---|---|
| 结构 | 单文件 `ReelLudic/catalog.json`：`{ version, entries[], activityLog? }` |
| 写入 | `CatalogStore.save` → **全量重写**（`JSON.stringify(clean, null, 2)`），每次改动写整份 |
| 删除 | **物理移除**（`entries.filter(e => e.id !== id)`）+ **笔记文件直接删除**（`EntryService.removeWithNote` → `io.deleteFile`）→ **不可逆、无回收站、无 tombstone** |
| 活动日志 | 上限 `ACTIVITY_LOG_LIMIT = 500`，超出截断最旧 |
| 备份 | **仅手动**：设置页「导出 JSON 快照 / 导入合并去重（标题+类型判重）」；无自动备份、无历史 |
| 读取 | `load` → `JSON.parse` + 逐条 `normalizeEntry`（字段级兜底），无 schema 版本迁移框架（`version` 字段读了但未用于迁移） |
| 外部变更 | vault 文件监听（500ms 防抖）兜底 |

### 演进建议（分三层，按优先级）

**P0 数据安全（建议进 1.0.4 批次 A）**

1. **写前保留滚动备份**：写盘前把旧文件复制到 `ReelLudic/.backups/catalog-YYYYMMDD-HHmmss.json`，保留最近 N 份（N=5），超限删最旧。成本低、价值最高（当前「全量重写 + 无备份」意味着一次异常写入即可丢整库）。
2. **写前 round-trip 校验**：`serialize → parseCatalog → entries.length` 比对，不一致则中止写入并提示（防止脏数据覆盖好数据）。
3. **写盘节流**：状态翻转/进度落库目前每次都全量重写；大库下需合并 300–500ms 内的多次写（与 vault 监听的 500ms 同量级）。

**P1 删除语义（1.0.4 或 1.0.5，取决于裁定）**

4. **回收站（回答「已删除的条目数据是否还保存」）**，两种设计：

   | | A. 同文件软删除 | B. 独立回收站文件 |
   |---|---|---|
   | 做法 | `entries[]` 内保留条目 + `deletedAt?: string`，视图层过滤 | 条目本体移出到 `ReelLudic/trash/<id>.json` + 一个 `trash-index.json` |
   | 可恢复 | ✅ | ✅ |
   | catalog.json 体积 | ❌ 不降（用户「过多条目」诉求未解） | ✅ 降 |
   | 导出/迁移 | 自动包含 | 需额外说明 |
   | 复杂度 | 低（但每个视图/统计都要过滤 `deletedAt`，漏一处即出现「幽灵条目」） | 中 |

   **推荐 B**（同时解决「可恢复」与「体积」），配：设置页「回收站（N 条）」入口（查看 / 恢复 / 彻底删除 / 清空）、保留期（默认 30 天自动清理，或纯手动）。
5. **笔记文件同进退**：现在删条目即 `deleteFile` 笔记（不可逆）。建议改为移入 `ReelLudic/trash/notes/`（或 `<笔记目录>/.trash/`），恢复条目时一并还原。**这是本项最关键的裁定点**——决定「手滑」是否可挽回。
6. **删除入口统一走新语义**：`removeWithNote` / `deleteEntries` / 设置页清理、以及 ④ 的气泡确认链。

**P2 规模（「过多条目未来怎么办」）**

7. **先量化再优化**：新增设置页「数据健康」面板 —— 条目数 / catalog.json 大小 / 笔记数 / 备份数 / 回收站数 / 各类型分布 / 最早与最新记录时间。无数据不决策（用户取向最小改动）。
8. 分级结论（供决策，非本版必做）：
   - **< 1k 条**（当前量级 ≈ 几十条）：单文件全量完全够用（< 500KB），只需 P0 三项；
   - **1k–10k 条**：分页/虚拟滚动（⑥）+ **activityLog 拆独立文件**（`activity.json`，它是唯一「只增不减」的部分）+ 写盘节流；单文件仍在 1–5MB 可接受；
   - **> 10k 条**：单文件全量重写的成本（每次落盘 5MB+）成为真瓶颈 → 才考虑「按类型分片 + 内存索引」或引入 SQLite/IndexedDB 作缓存层（文件仍为真源）。**不建议提前做**。
9. **schema 版本迁移框架**：`migrateCatalog(raw)`（按 `version` 逐级迁移 + 幂等 + 单测），为将来「删字段 / 改语义」留出正式通道——当前 `normalizeEntry` 只能做字段级兜底，无法表达语义变更。

**P3 导入健壮性**
